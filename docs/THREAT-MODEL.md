# Threat model

**This software has had no independent security audit.** It is a stage 1 build for a small group of friends. It uses a well-known MLS implementation (OpenMLS) and RustCrypto/dalek primitives and implements no cryptography itself, but the way the pieces are combined (device certificates, the relay protocol, authorization rules, recovery) is new code that nobody outside this project has reviewed. Treat it as "much better than nothing, not yet proven".

## What we protect, against whom

| Asset | Protected against | By |
| --- | --- | --- |
| Message text, edits, replies, reactions, attachment bytes, file names and types | The relay operator and anyone who breaks into the relay; network observers (add TLS on top, see DEPLOY.md) | MLS application messages (AEAD per sender key), attachments encrypted client-side before upload |
| Community names, channel names, roles, display names, invite settings | Same | They live only inside MLS group-context extensions and MLS messages |
| Who may speak or change membership | A malicious member, a malicious relay | Signed MLS commits; every client enforces the same group-local rules and skips commits that break them |
| Being put in a community without agreeing | Anyone who runs a community, however many devices you have | A device accepts one only if it asked, or the table holds that community's consent signed with your own account key (DESIGN.md 7.2). Test: `two_devices_are_not_a_way_to_pull_someone_into_a_community` |
| Later messages after someone is removed or a device is revoked | The removed member / lost device | Commit with a path: new epoch secrets they cannot derive. Tested by feeding the removed client the whole relay log |
| Identity of a friend | A relay or stranger impersonating them | Account key = account id; device certificates signed by it; safety numbers for out-of-band verification |
| Keys and history on a stolen powered-off laptop | A thief with the disk | Argon2id + XChaCha20-Poly1305 over the whole state; side files sealed with the same key |
| Message integrity and ordering within a group | A relay that reorders, duplicates, withholds | Strict `seq` processing, gap detection, MLS epoch and generation checks, exactly-once ids. A relay can still *delay or drop*, and the client says so |

## What the relay can see (exactly)

The relay is treated as hostile. This is everything it stores or observes. Verified by `relay_holds_no_plaintext` (greps all relay files for message text, file names/contents, channel/community/display names) and by the table list in that test.

**Stored (tables `devices`, `keypackages`, `group_members`, `group_auth`, `acl_demoted`, `entries`, `welcomes`, `rendezvous`, `blobs`, `usage`, plus a `blobs/` directory):**

* **Device registry**: for each device its public key, its account's public key, the certificate (including its creation time), and whether and when (signature only) it was revoked. So the relay knows which devices belong to one account.
* **Key packages**: opaque to it, but they contain the same certificate and public keys. It knows how many are left per device.
* **Group membership list (ACL)**: for each random group id, the set of *accounts* allowed to read and write it. So it learns the social graph at account level: which accounts share groups, group sizes, when members are added and (after the grace period) removed. It does not know names or purposes.
* **Group authority**: for each group its root (control group), and for each root its current owner account and how many times ownership changed. So the relay *knows* which channels belong to which community, and who owns it. It also sees an account's owner-signed admin grant whenever that account changes an ACL, and holds the accounts whose grant the owner withdrew. It does not hold a list of current admins, but it learns them as they act.
* **Usage**: bytes each account has posted, and the size and uploader of each blob, to enforce quotas.
* **Log entries**: `(group id, seq, client random id, tag byte, ciphertext)`. The ciphertext size is padded to a multiple of 256 bytes by MLS. The tag tells it: application message, commit (a membership/epoch change), rejoin request, join request.
* **Welcome inbox**: for each recipient device, MLS Welcome ciphertext, deleted when acknowledged.
* **Join requests** (the only plaintext JSON it holds): invite id (random), the joiner's certificate (account and device keys), a signature, and the account's consent to that community (a signature and a time). So it knows *which account asked to join which group id*, and when they pressed the button. The community invite's secret key is never sent.
* **Rejoin requests** (plaintext): the device's certificate, a nonce, a signature. It learns that a device lost state.
* **Blobs**: ciphertext, exact size, random id. It knows which device uploaded and which devices downloaded each blob, and when, but not which message or channel it belongs to.
* **Rendezvous** (device pairing): a sealed box it cannot open, for at most 15 minutes, under a random id it only learns from the request itself, with the account that wrote it. The pairing code is a bearer token in both directions: whoever holds it can write the approval into the box first, and the new device then becomes a device of *that* account (the check digits derive only from the new device's key). Send the code only to yourself; the app does not yet make the new device confirm whose account approved it.

**Observed, not stored:** IP addresses and timing of every request (inherent to any server; use a VPN/Tor if that matters), and **which device posted each entry** because requests are signed by the device key. Message *timing and size* is visible; who is talking to whom inside a group is *not* visible beyond "this device posted this entry" (MLS hides the sender inside the ciphertext, but the HTTP request does not).

**Not visible to it:** message text; attachment contents, names, types; community, channel and display names; invite limits; who reacted or edited; which entries are replies; typing indicators (on by default for new accounts, off for an account that turned them off; they are ordinary padded messages); room and community colours (carried inside the encrypted community table, signed by the owner); live events (sealed with a key only the room's members derive, held by the relay in memory for seconds and never stored; see "The live channel" below); read state (there are no read receipts); search queries (local).

**What a hostile relay can do (and what we do about it):**

| Attack | Outcome |
| --- | --- |
| Read | Only the metadata above. |
| Drop or delay entries / deny service | Possible. Detected as gaps (`seq` is gap-free) and shown. Cannot be prevented by design: this is a centralized relay. |
| Reorder or duplicate | Neutralized: processed strictly by `seq`, de-duplicated. |
| Show different logs to different members (fork) | Possible in principle. MLS makes the forks cryptographically distinct, clients that cannot follow report it (future-epoch / gap messages). Not fully detectable without a gossip channel between members. |
| Replay old requests | Within a 10-minute window; mostly idempotent (ids). A request made for a relay that binds (the relay says so in `/v1/info` and has its own random id; the device then signs over that id and sends only `X-Commons-Auth2`) is refused by any other relay, so a copy taken from the wire or a log cannot be played elsewhere. A relay operator who tells its own clients the id of another relay can still replay to that relay what those clients send; relays and clients from before this sign the old way, which any relay the device is registered on accepts. |
| Forge a message or a member | Not possible without a device key; certificates are verified against the account key. |
| Serve a wrong key package / invent a device | Rejected: credential must be a valid certificate for the expected account and device. |
| Hide a device revocation | Possible (relay is the directory). Mitigated by also broadcasting the revocation inside every community. A device that never sees either could still be added by a stale admin. |
| Block a person from joining or being added | Possible (omit their key packages or requests). Visible as "waiting". |
| Lift a call cut-off, or cut someone off from calls | The relay keeps a `call_denied` list (accounts an admin cut off from a group's calls, kept apart from membership). The relay can add or drop entries, so it can deny a call to a member or let a cut-off member back into the room's token service; it still cannot decrypt the call, and members' clients stop trusting a removed device's media keys at the next epoch. |
| Make a client believe it was removed | Possible ("denied"); the client labels it as unconfirmed and keeps its local state. |
| Lie in `group_members` ACL | Gives it nothing to gain beyond what it already has; it can only cause denial of service. ACL rules protect against members, not against the relay itself. |
| Tell a client it has caught up when it has not (omit `more`) | The same as withholding entries. |

## Joining with a password (invite passwords)

An admin can choose a password when creating an invite and tell it to a friend, who types it in the app together with a name. The password does not replace the invite: it is a way to deliver one.

**How it works.** The app derives two things from the password with Argon2id (64 MiB, 3 passes), salted with the relay's address in canonical form (scheme, capitals, a final slash and a default port do not change it, so a friend can type the address any way; invites made with the earlier, spelling-dependent salt are still found, in the same lookup on a current relay): a lookup id and an encryption key. The ordinary invite link (which already carries the relay's sign-up secret when there is one) is sealed with XChaCha20-Poly1305 under that key, padded to whole kilobytes, and filed on the relay under the lookup id. The friend's app derives the same two values, asks for the sealed copy, opens it and joins as if the link had been pasted. Everything an invite link is checked against still applies on the community's side: the invite's own expiry and use count, bans, the roster and owner rules, and an admin's client being the one that adds the person.

**What the relay learns.** The lookup id and the ciphertext (a fixed-size block, so its size says nothing about the link), which account filed it, when it expires and how many fetches remain. It never receives the password, the key or the link. It also sees that someone looked an id up, and from where it can see (behind Tailscale Funnel: nothing useful). A wrong password, an expired copy, a revoked one and a used-up one get the same answer.

**What a weak password risks.** Whoever guesses the password can join the community, up to the invite's use limit and expiry; that is the same as being handed the link. Guessing works in two ways.
* *Online*: asking the relay. It allows 8 lookups per id, 12 misses per caller (the peer address, or the address a reverse proxy in front reports in `X-Forwarded-For`) and 400 misses per 10 minutes for the whole relay. A caller that has spent its own budget is refused every lookup, hits included, so a guesser gains nothing by luck; the whole-relay budget is the backstop against many addresses, and one caller cannot spend it for everyone (0.3.5 had one budget of 40 for the whole relay, so forty junk lookups from anyone kept every friend from joining for ten minutes). Filing a sealed copy under an id another account already holds is answered like success and stores nothing, so the filing route says nothing about other people's passwords. At these rates a suggested password (about 56 bits) is out of reach in any realistic time.
* *Offline*: someone who obtains the relay's database (or who is the relay's operator) holds the lookup id and ciphertext and can test guesses at the cost of one Argon2id run each. A password under 50 bits is refused at creation (35 before 0.3.6: the estimator then scored any word outside its small list as random letters, so two ordinary words passed), every run of letters counts as a dictionary word, and the suggestion (five random words from a list of about 1000 and a two-digit number) is about 56 bits. That is good against a thief of a copy of the database for as long as the invite lives; it is not good against a state-sized budget and decades. The default is therefore 7 days and one use, a password invite lives at most 30 days, and the relay deletes the copy when it expires, when its fetch allowance runs out, or when the inviter revokes the invite. If you are inviting someone to something sensitive, use a longer password (the screen says when yours is short) or a link.
* A password that is also used elsewhere, or is reused for a second invite on the same relay, is as strong as its weakest use. A password already in use on the relay is refused (the inviter is told so; that is also a small yes/no signal to any registered account, rate limited per account).

**What the inviter should know.** The password is not stored by the app after the screen that shows it. Anyone who sees it (screen, message history, a shoulder) can join until the invite is used up or revoked; revoke from the same screen. A relay with no sign-up secret lets anyone register; one with a secret can only be joined by password because the sealed copy carries that secret to the friend, so a password is as sensitive as the secret for its lifetime.

**The friend's device password.** It protects the local vault exactly as before (Argon2id, unchanged). It is typed once with a show button instead of twice. The recovery key is not shown before joining; a reminder stays on screen until the person says they saved it. Until then, losing the device loses the account.

**Older relays and clients.** A relay without this feature answers its info request without the `pwinvite` flag; the app then says the server is too old and offers links. Old links and old clients are unaffected and remain the fallback.

## Voice rooms and screen share (stage 2): what each server can see

Two servers are involved. Assume both are run by the same person and both are hostile.

**The relay (token service) additionally learns**, when someone calls `call-token`: the random group id (it knew it already), the calling device and account, and the time. So it learns *who joined which room's call and when*, not that a call has audio, video or a screen share, not names. It holds the LiveKit API secret, so it can mint tokens for anyone: that lets the operator join a room as a silent participant (see below), never decode it.

**The LiveKit server sees, exactly:**

* IP addresses of every participant (and, with TURN, of nothing more than the TURN allocation); join and leave times; the room name, which is a one-way hash of the group id (it cannot be linked to a room without knowing the group id, which the relay operator does, and it is the same person in the default setup); participant identities, which are device ids (stable across calls: it can tell that the same device returns, and, together with the relay, which account).
* Whether each participant is publishing audio, camera or a screen share (track type), publish and mute state, the video resolution and frame rate it negotiates, and simulcast layer choices.
* **Who is speaking and when.** The audio level travels in an RTP header extension the server needs for active-speaker detection, and silence suppression makes silent packets tiny, so talking time is visible even though content is not. Packet sizes and timing of voice leak speech rhythm (the well-known variable-bit-rate effect, with the first byte of each Opus frame and the packet size in clear); a determined server operator may learn something about *what* is said from sizes alone, which is why this is called "cannot hear", not "learns nothing".
* Sizes, timing and volume of everything, hence who is sharing a screen and for how long, and the screen's rough activity (static document vs. moving video) from the bitrate.
* LiveKit's own client info: SDK version, browser and OS strings.

**It cannot see:** audio, video or screen content (frames are AES-GCM encrypted in the sender's browser with keys the server never gets), display names, group, room, community names, who is in the community but not in the call.

**What a hostile media server or operator can do.** Hear nothing. Drop, delay or replay packets or end the call (denial of service; detected as silence or the "reconnecting" banner). Join the room with a minted token and record ciphertext: tested (the operator tab sees the forwarded Opus payloads; a plaintext control stream decodes to the tone, ours decodes to nothing). Add a fake participant: clients block any sender whose device id is not in the room's MLS group and any track not marked encrypted. Mark a track "unencrypted" to make clients play it as is: clients refuse to play tracks not marked encrypted, so this ends in silence, not in plaintext playback. Replay old ciphertext: harmless audio replay, same as a recording of encrypted data; frames are not individually sequence-protected beyond AES-GCM's IV (this is a limit of LiveKit's frame scheme).

**Members.** A current member can derive every sender's key (keys are per sender for separation, not for authenticity), so a malicious member can inject audio that appears to come from another device's identity if they also control the server's routing. Group-level authentication, not sender-level: same trust level as the text channel's members. A removed member keeps the media they already received and, if still connected with a modified client, keeps receiving ciphertext they can no longer decode after the next epoch; clients also stop trusting their identity at once. For up to the 3 s grace period after a rotation, frames under the previous epoch's key are still accepted, so a removed member could inject audio in that window only if the server still routes them (their token is not renewed; the SFU does not itself evict them: an operator who wants that calls LiveKit's `RemoveParticipant`).

**The call page holds the media keys.** A malicious script in the web view could read them; the same page can already read the decrypted messages shown in it, so this adds no new class of exposure, but the web view and its content security policy (`script-src 'self'`) are part of the trust base.

**Platform limits.** Frame encryption needs a browser or web view that provides insertable streams. Where it does not exist the app says so and does not start the call. See `docs/CALLS-PLATFORMS.md`.

## The live channel (unstored live events)

Camera-tile drags and holds, wall strokes and wall snapshots are *live events*: useful for seconds, worthless afterwards. They used to be ordinary MLS application messages. That made each one a permanent entry in the relay's append-only log, charged to a lifetime quota, and a state rewrite for the sender. It would also have been wrong to simply stop logging them: every MLS application message advances the sender's ratchet, and the groups tolerate only 2000 skipped steps (`SenderRatchetConfiguration::new(64, 2000)`), so a member offline while unlogged events piled up could never again read that sender's next real message. So live events do **not** go through the MLS application ratchet at all.

**How an event is protected** (`crates/core/src/live.rs`):
* *Key.* `MLS-Exporter("commons-live-v1", group id, 32)` of the group's current epoch: the same derivation as the call keys with a distinct label. Every current member has it; nobody else does; a commit starts a new one. Deriving it reads the group and changes nothing, so sending a live event advances no MLS state and saves nothing.
* *Seal.* ChaCha20-Poly1305, a fresh random 96-bit nonce per event, plaintext padded to a multiple of 128 bytes. The additional data binds the group id, the epoch and the sending device. The event's kind is inside the ciphertext and under the signature (so it is bound, and the relay does not learn it).
* *Sender.* The sender's device key signs, inside the ciphertext, the group, epoch, device, nonce, kind, time and data. A receiver verifies against the device the relay names, which must be in the group's current roster. So one member cannot speak as another (the group key alone would allow it), and a removed member is not heard even for an epoch they still hold a key for. The nonce is under the signature, so an event cannot be re-sealed with a new nonce to evade the replay filter.
* *Order with the log.* A wall lock or clear lives in the signed community table, which travels through the log; a stroke that follows it travels by the live channel, which has no order with the log. So each event also carries, under the signature, how far its sender had read the community's control log (one more while a change of its own is on its way in). A receiver that has not read that far holds the event (up to 10 seconds, at most 16 per sender and 64 in all) and delivers it once it has; otherwise a stroke drawn on a fresh wall could arrive before the clear and be thrown away, or a stroke by a non-owner after a lock could be taken by a device that has not yet heard of the lock. A hostile sender can only make its own events wait or lapse by claiming too far a position.
* *Epochs and replay.* Events under the current or the immediately previous epoch are accepted; earlier ones are dropped; one from an epoch not yet reached is held up to 10 seconds. Each nonce is taken once; events older than 30 seconds (by the signed time) or more than 60 seconds ahead are dropped. Receivers keep the old per-sender rate limit (20 a second from this channel) and buffer caps, and nothing is stored in history.

**What the relay does** (`crates/relay/src/live.rs`): `POST /v1/groups/{gid}/live` takes sealed blobs from a signed-in device whose account is a current member of the group, and `POST /v1/live/poll` long-polls (up to 25 s) for news in the rooms the caller belongs to. The buffer is in memory only, never written to the database or disk, per room: events are kept 30 seconds at most, at most 1500 events and 3 MiB, at most 450 events and 1 MiB from one device, 30 posts a second per device per room, 64 MiB for the whole relay; a poll answer carries at most 200 events and 512 KiB per room. A restart empties it.

**What the relay learns, exactly.** For each event: that device D, of account A, posted a blob of N bytes (padded, so N is a bucket, 128-byte steps) to group G at time T; and which devices poll which rooms, and when. It sees no plaintext, kind, key or signature, and it cannot forge an event (it lacks the room key and any device key). It could always see roughly this for log entries; the difference is that it now also sees *polling* (a device asks about all its rooms every few seconds; each answer says which of those rooms had events), and that live events leave no trace on disk. A hostile relay can drop, delay, reorder, or replay (once only: nonces are remembered) live events: a denial of service for a feature that is optional, never a break of content. It cannot deliver events to a non-member (membership is checked on every post and poll), but one removed from the relay's list only after a delay (`acl_delay_secs`) can still *fetch* sealed blobs in that window; they cannot open them once the room has moved to a new epoch.

**What a member can do.** Any current member holds the room key, so a member can read all live events of the room (as for any message). Because every event is signed by its sender, a member cannot impersonate another member. A malicious member can flood within the rate limits (30 posts a second per device per room at the relay; receivers take 20 a second per sender), which costs receivers CPU and the relay's capped memory, not durable storage.

**Limits we accept.** (1) The previous epoch's key is held only in memory: a client that restarts at an epoch boundary loses at most the events of that moment. (2) A removed member who is still connected can post sealed events under an old epoch until the relay's list drops them; receivers reject them because the sender is not in the roster. (3) Versions before this channel (0.3.0 and earlier) only read the log: on a relay that has the channel, they no longer see live events from newer clients (tile drags, wall strokes). Chat, calls, colours and the wall's saved state through the usual paths are unaffected, and they get no errors. They still send live events through the log, which new clients still read.

## Hosting through Tailscale Funnel (deploy/go-online.sh)

What it adds to the above, when the relay runs on your PC and friends reach it on one public port:

* **Tailscale** runs the public entry point. It sees friends' IP addresses, the host name (TLS SNI), timing and volume. TLS ends on your PC, with a certificate only your PC holds, so it does not see the requests or the media, and those are end-to-end encrypted inside anyway.
* **The relay sees every connection as coming from 127.0.0.1**, so it logs no friend's IP address, and it cannot rate-limit per address (its limits are per account and whole-relay).
* **The front** (`--front`) routes by first bytes and parses nothing else. Only LiveKit's `/rtc` is reachable through it, never its admin API. Tested: `/twirp/...` gets the relay's 404.
* **The invite secret is required**: go-online.sh makes one and `--front` refuses to start without it. Anyone holding a link that carries it can make an account. They still cannot read a community they were not let into. It gets a stranger as far as the quotas, so keep the link private, and change it (delete `~/.local/share/commons-host/invite-secret`, go offline and online) if it leaks. Community invite links carry it too, for the same friend-sized trust.
* **What is public**: `/health`, `/v1/info` (says that a secret is needed), `/join`, `/download/`, `/update/`. The first install comes from your PC unsigned for Windows and macOS: whoever controls that PC controls what your friends first install. Updates after that need the updater key as well (below).
* **LiveKit's TURN** relays media for call members. It has to be allowed to reach its own SFU on loopback (`allow_restricted_peer_cidrs: 127.0.0.1/32`), so a call member holding a token can also send UDP to other loopback services on the PC through it. Its TCP port ignores `bind_addresses` and also listens on your LAN; it does nothing without a token's credentials. Friends only: this is another reason to keep invites private.
* **No third-party STUN**: LiveKit hands clients Google and Twilio STUN servers when TURN over UDP is off; the client strips them before any connection exists (test H17).

## Updates (docs/UPDATES.md)

* **Who can push an update:** whoever holds the updater's private key (`~/.config/commons/updater.key` and its password, on the host's PC only). The apps install a file only if its minisign signature checks against the public key built into them, and only if the signature was made for the version announced. The relay, Tailscale, or anyone on the path can therefore not slip in a changed app; with the key, they could.
* **What the relay (or whoever controls it) can still do:** withhold updates, or keep serving an old manifest. It cannot make an app go back to an older version (only newer versions are offered, and a signature names its version), and it cannot point an app at another server (the manifest and the files must come from the account's own relay; redirects are not followed).
* **What the update check tells the relay:** that an app asked, when, and which file it downloaded (so which system it runs). The request carries no account and no signature.
* **Nothing installs by itself:** the person is asked every time, and nothing happens during a call.
* **Not code-signed for the systems:** Windows SmartScreen and macOS Gatekeeper still see an unknown publisher on the first install. The update signature is Megatron' own check, on top.

## Game keys (docs/GAME-KEYS.md)

Settings live in the encrypted state of one device; which games you play never reaches the relay or another device. The helper reads only the keys you set, only during a call, and sees programs by name only. Through the call bridge the tab learns one thing: a game key is holding the mic, with that program's name (a browser extension with access to the tab could read that). On Linux, joining the `input` group, if you choose to, lets every program of yours read all keys; Megatron does not ask for it and keeps only the keys you set.

## Message notifications (crates/core/src/notify.rs)

The background part of the browser version (and the desktop app's core) shows a system notification for a new message when no mega window is being looked at, even with the browser closed. It reads the message from the local history and hands it to this computer's own notification service (freedesktop over D-Bus, Notification Center, Windows toasts). Nothing goes through a push server of Google, Apple or Microsoft, and nothing is sent to the relay for it; no new network traffic exists. By default a notification says who wrote and in which room ("New message from Ben in #music") and nothing of the text; "Show message text in notifications" (Settings, off by default) adds the first 100 characters. Text from a message this device could not decrypt is never shown: only decrypted history is read. What the operating system does with a notification is outside mega: a lock screen, a notification history or a screen reader can show what a notification says, which is why the text is off by default. While a mega page is open and hidden, the page shows the notification through the browser's Notification API instead (the bridge hands it over through the page's heartbeat) and the background part stays silent. The rules (global mode, per-room mutes, the text switch) are stored in the data folder (`notify.json`, not secret, no keys) on this device only. A hostile community member can cause a notification per room per five seconds at most, because bursts are folded together; muting a room silences it completely.

## Other adversaries

* **A malicious or compromised member**: can read everything in the groups they are in, share it, and can spam, up to the relay's per-account quota. Cannot change membership or roles without the right role (all honest clients skip the commit), and cannot change a group's relay ACL at all. An admin can remove and add people, also at the relay, including other admins there (the relay cannot tell admins apart; the owner's client puts them back); the owner is irremovable. Two members can show the same name with a modified client; everyone then sees a short account tag next to it. A removed member keeps what they already received.
* **Someone who steals an unlocked, running device or its decrypted memory**: wins everything that device could read, and also holds the **account key**, which is present on every device. They could enroll more devices for that account and revoke yours. **Revoking the stolen device does not stop this**: the key it holds is the account key, and nothing tells its new devices apart from yours. You and the members get a "new device" notice each time, and you can revoke each one, but there is a window every time. If it keeps happening, move to a new account. A trusted-device split (account key only on devices you mark) is planned and is what would close this.
* **Someone who steals a powered-off device**: needs the passphrase. Argon2id (64 MiB, t=3) slows guessing; a weak passphrase is still weak. There is no OS keychain integration or hardware key in stage 1.
* **Malware, keyloggers, screen capture, clipboard snoopers, a compromised OS**: out of scope; end-to-end encryption does not help.
* **Recovered device and communities you left**: a device made from the recovery key does not know which consents you took back, so a community owner who kept your old entry can add it again. Only communities you once joined; leave again if it happens. See DESIGN.md section 7.4.
* **Lost recovery key and all devices**: the account is gone. The recovery key is as powerful as the account.
* **Targeted attackers who obtain the invite link**: whoever has a link can *ask* to join; an admin's click is not required (links are meant to be sent privately), so use one-use links and short lifetimes (the UI defaults to one use). A one-use link admits one person even when several ask at once. Kicked users are banned by account.
* **Strangers who can reach the relay**: with an invite secret set they cannot register at all. Without one they can register, up to a rate and account limit, and use their own quota. Join requests from non-members are rate limited per device and per community; a real one can be delayed by a flood from many devices, and is sent again.

## Cryptographic and design limits to know about

* Forward secrecy and post-compromise security are those of MLS: they come from commits. A group that never changes membership keeps one epoch for a long time unless clients commit. Stage 1 does **not** schedule periodic self-update commits (only after restore, and on membership changes). Past epoch secrets are kept for 8 epochs so late messages still open.
* Local history is stored for good, encrypted at rest with the passphrase key. Deleting a message deletes it for everyone's *display*; it cannot erase copies someone made.
* "Delete" and "edit" are advisory messages: a modified client can ignore them. Authorization of who may delete is enforced when displaying, not by cryptography.
* Key package and leaf lifetimes are set to 5 years so a quiet group does not break; this trades some hygiene for reliability.
* The device key is used both to sign MLS messages and to authenticate to the relay (different, domain-separated message formats).
* Group and channel membership is a single MLS group per channel: the relay sees the same account set for each channel of a community.
* Timing and size side channels exist (padding is coarse, 256 bytes; attachment sizes are exact).
* Typing indicators are on by default, and an account from before this default is switched on once when it next opens (the options room turns them off, and that choice then sticks); when on, they tell the relay "a packet was sent now".
* **Owner colours** reveal nothing new to the relay: they travel in the community's encrypted table (the group-context extension) like the community name, as an owner-signed document. The relay sees the same thing it sees for any table change: a commit was posted, its size, and when. Members can read the colours; only the owner's signature makes them count, so an admin or member cannot change them (they can drop them, or put an older owner-signed document back; devices present keep the newer one they hold, every admin's device and the owner's put the newer copy back at once and then at growing intervals up to ten minutes, so a hostile member cannot make them commit faster, and a commit by anyone but the owner that regresses the document raises a notice naming the sender. A newcomer is admitted by an admin's commit, which carries the current document, so a newcomer never reads the rolled-back one; see docs/security-0.3.6.md M1 for why such a commit is still merged rather than refused: refusing what every earlier version accepts would split the community). A member on an older version ignores the field.
* **Rings** (ring a voice room, or one person in it) are a message kind of their own, `Ring { id, ts, to?, end? }`, sent inside the voice room's own MLS group like any message. The relay sees one more padded message from that device at that time, and nothing of the kind, the room's name or who is rung. Members of the room (everyone in the community, since every room holds every member) learn who rang, when, and, for a ring to one person, who: `to` is inside the encrypted envelope, so nobody outside the group learns it, but every member's device can read it (a ring to Bob can be read by Carol's device, which ignores it). Receivers enforce, in the core and not in the UI: the sender is a current member of that room's group; the room is a voice room; the ring is no older than 45 seconds by the sender's clock and no more than 60 seconds ahead of ours (so a device catching up on a log never rings for an old call); at most 4 rings a minute are taken from one sender (and 8 take-backs); a ring from our own account is ignored (so your other devices never ring you); a ring for someone else is ignored; one ring id rings once. A ring is sent best effort and never retried (an unsent one is dropped after 10 seconds), is never stored in history, and its card ends after 30 seconds, on answer or decline, or when the caller takes it back. What a hostile member can do: ring everyone in the room at the rate limit (4 a minute each, so a nuisance, not a flood), and lie about the time within the 45 and 60 second windows; they cannot ring someone outside the room, cannot ring as someone else (the sender is the MLS sender), and cannot make a device show a card for a room it is not in. Declining or answering on one device does not stop the card on your other devices. Nobody whose app is closed is reached: there is no push service, by design; a person with the app open in a background tab can be rung, but a browser may slow a long-hidden tab's timers enough to miss a 30 second ring. A system notification is shown only if the page is hidden and the person has already allowed notifications for the page; the notification text (who, room, community) goes to the operating system's notification centre, like a message notification would. A member on an older version notes "newer version" once and otherwise ignores it.
* **No private two-person rooms yet.** A "call one person" room that only two members hold is not built, because the current protocol cannot express it without a change that would break or weaken older clients: (1) the relay accepts a new room only from an owner or granted admin, so an ordinary member cannot create a group at all; (2) a Welcome to a room is accepted only from the owner or an admin, and a commit that adds someone else only from an admin; (3) every room must be listed (with its name and kind) in the community table that all members read, and every admin's reconcile loop then adds every community member to every listed room, so a room for two would be filled with everyone, and an unlisted one would be reconciled by nobody (a second device of either person, or a removal after a kick, would never reach it). Each of these is a rule in deployed relays or clients; relaxing them would let any member make rooms and pull others into them. See docs/DESIGN.md, "private channels", which remains future work.
* **History on a new device** (0.3.6, docs/history-transfer.md). A freshly paired device posts a signed request to the account's other devices through the relay's per-device inbox; the device where the person says yes (the tick box when approving the pairing, or Send under Devices) sends its rooms' messages in chunks sealed to the new device's own key and signed by its device key, through the same inbox. The relay carries ciphertext it cannot tell from Welcomes except by size (chunks are padded to 4 KiB steps); no group, epoch or other member is involved; a revoked device gets nothing more. What a stolen unrevoked device can do is unchanged: it could already pair devices and approve anything.
* **Calling one person (direct calls).** A private two-person room inside an existing community is still impossible under the current rules (the relay accepts a new room only from an owner or granted admin; a room Welcome is accepted only from an owner or admin; every room is listed in the table that all members read and is filled with every member). So a one-to-one call is not a room: it is a **hidden two-person community**, which the existing machinery already keeps private. Nothing about groups, tables, the relay or any existing envelope changed. The caller founds a community (named "Direct call (open in a newer Megatron)", which is what an older app would show), with one voice room named "call", and sends the other person one new end-to-end encrypted envelope, `Direct { id, ts, to, nonce, link }`, inside a room the two already share (the same way a ring travels). The `link` is an ordinary invite to the new community with its use limit set to 2 and a 10 minute life, without the relay's sign-up secret, and (0.3.6 on, when the other person's profile says `direct_sealed`) with a throwaway key in its place: the invite's real secret key travels in the same envelope sealed to the other person's account key (`sealed`), so nobody else in the shared room can sign a join with what they read, whatever version the founder's admin devices run. For a 0.3.5 peer the key is still in the link, as before. The callee's app joins it on its own and then rings through the ordinary `Ring`.
  * **What the relay learns.** For the offer: one more padded message in a shared room, from that device at that time, and nothing of its kind or content. For the community: exactly what it learns for any group. A two-member group exists, who its two accounts are (the relay's access list for the community and its voice room holds the two account keys, and it sees the group's commits and the Welcome that adds the second person), when they joined, when they post, and the LiveKit room name if a call server is used. It cannot tell this group from any other two-member group: the marker (below) is inside the nonce, which is only in the encrypted group context, and the relay never sees nonces or names. It learns that two accounts that share a community with each other also have a private pair group, which it could already guess from the traffic. Calls themselves are exactly as for any voice room (frames are end-to-end encrypted with keys exported from the room's MLS group; the call server sees who connects and when).
  * **What other members of the shared room learn.** The offer is readable by every member of the room it travels in, not only the person it names: they learn that A offered B a call, when, and the invite link. They cannot use it: see the marker. They do not learn the community's name, room, members after the fact, or anything about the calls. Nothing is stored in history (the envelope is best effort, never retried, dropped from the sender's outbox after 10 seconds and not kept by receivers).
  * **The marker, and why it cannot be used to pull someone in.** A direct community's nonce is `salt (16 hex) | tag (16 hex)` with `tag = sha256("commons/direct/v1", founder, peer, salt)[..8]`, and the community id is the hash of founder and nonce, so the id itself commits to exactly two accounts. To everyone who does not know the peer's account the nonce looks like any other 32-hex nonce. The receiver of an offer joins automatically only if all of these hold, as one pure function (`direct::offer_check`) the same way `ring_check` is: the sender is a current member of the room the offer came in; the offer is for this account (`to`) and is not from this account; it is no older than 45 seconds and no more than 60 seconds ahead; the link's owner is the sender and its relay is ours; the nonce hashes with the sender to the link's community id and its tag verifies for this account as the peer (so an ordinary community, a direct community of the sender and somebody else, and a community the sender did not found are all refused); we are not already in it; the sender is not on our "stopped calls" list and an earlier join to that community was not refused (a ban is a refusal); at most 2 offers a minute from one sender, 6 automatic joins an hour in all, 16 direct communities held, and at most 2 of them founded by any one account (so a stranger sharing a room cannot fill the slots). Once in, every change of the community is re-checked: if it ever holds a third account, a text room, or a second room, the community is marked bad, is never shown, and the receiver's app leaves it (the founder can still do this to their own state; only the other person's app acts). **Admission** is bound as well: the founder's app (every admin device) refuses any join request to a community that carries the direct name or the marker unless the joiner's account verifies against the nonce, so a third member of the shared room who reads the offer and uses the invite is refused ("that invite is no longer valid"), as is anyone else. **Bans** are honoured: a founder's ban in the community's table refuses a join as for any community, and the founder does not offer to a banned account. **Blocks:** this version has no general block list; the "stop calls" button in the direct area (per account) is the block for direct calls, and refuses and leaves the direct community of that account.
  * **What a hostile member can do.** Send offers naming the receiver at 2 a minute: each at most joins the receiver to a two-person community that the hostile member founded and that the receiver's app then shows nowhere but in the "direct" area, listing the hostile member's name; the receiver can press "stop calls". The member cannot make the receiver join a community of anyone else, an ordinary community, or one that is not exactly a two-person voice-only community with the receiver as its one peer. Shape is checked after joining, not trusted before.
  * **Older apps.** An app from before this change cannot take part. Its handling of everything involved is the handling of things it does not know: the offer is an unknown envelope kind, so it notes "newer version" once and does nothing (the same note a ring or a live event already produces); it never joins the community, so a direct community never appears as a server on it. The Profile it sends has no `direct` flag, which is how a caller's app knows to say "this person is using an older Megatron" up front (the flag is on every profile a current app sends, and is sent once after an update). If no profile has been seen yet, the call is made and the interface says plainly that it only works if the other person has a newer mega open, and a ring nobody answers ends after 30 seconds. Known limit: **a second device of the caller or the callee that is on an older app** is not stopped from being added to the community by the ordinary rules (the account's consent is in the table, which is how every second device joins). On such a device the community shows as a server called "Direct call (open in a newer Megatron)" with a room "call". It is the account's own community and nobody else can see it, but it is a stray entry until that device is updated or leaves it.
  * **Limits.** The founder's other devices hide the community by its name until the other person has joined (before that the marker cannot be checked, since the peer is not yet a member); if the other person never joins, those devices go on hiding it. Declining a ring does not delete the community; "stop calls" does leave it. An offer is not stored, so a callee whose app is closed at the moment never sees it.
* **The camera stack order and the shared wall** ride on live events, so the relay learns nothing beyond "a packet of this size was posted now by this device". Everything inside (which tile a person holds, the order, the drawing, the questions and answers) is end-to-end encrypted like a message. What members learn: who is dragging which tile (visible to people in the call), and who drew which cells (a cell carries its author's account, which is how ties are broken). Each event stays in the relay's log like any entry, so the apps send them sparingly: a 3 second drag is about 9 events at most, drawing at most 2 events a second per person with at most 200 cells each, nothing while idle, and nothing into a room where nobody is around to see it. The wall is kept on each device inside the encrypted state (a capped field, written on a 20 second debounce). **Lock and clear** are fields of the owner-signed style document in the community table (a set of locked rooms and a per-room wall generation), so they are durable, reach late joiners and cannot be forged: a lock makes receivers drop strokes from anyone but the owner, a clear raises the generation so strokes and snapshots of the old generation are ignored by everyone, including a device that was offline. A snapshot (a member's copy of the wall, sent to someone who just opened the room) carries per-cell authorship that only the sender vouches for, since cells are not individually signed; so while a wall is locked only the owner's snapshot counts, every author a snapshot names must be a member of the room, and one sender may introduce only a few new authors. Older apps note "newer version" for these events and ignore them; they also read a style document that has the new fields (unknown fields are skipped, and a document without them is byte-for-byte what it was).
* **Presence on the cards** (small dots in a person's colour on the card a friend is looking at). Each device sends `pres.f` live events on the unstored channel only (see "The live channel"): the app asks the core whether events really travel on that channel and, if the relay or the room has fallen back to the log, sends nothing at all, so presence never makes a permanent log entry. An event says: which community and which card (a room id, or the community's own card) the sender has settled on, or that they left. It goes into one text room of that community (the lowest-id one that takes it), so **only members of that community learn what you look at there**, and a member of another community you share learns nothing about it. Members of the community can read it like any live event, so **fellow members learn that you are in the app, on the card screens, and which card you rest on, to the second, for as long as you do** (and, from the silence after, roughly when you stopped). Nothing is sent while the tab is hidden or you are in a chat, and a person counts as gone after 45 seconds of silence. Sending is limited to when the focused card changes (after it has been the same for 0.7 s, so scrolling past cards sends nothing for each), at most 2 events a second, plus one heartbeat about every 20 seconds while you stay. **The relay** sees what it sees for any live packet (a sealed blob of a bucketed size posted by this device to this room at this time, nothing of kind or content), but because of the heartbeat it can tell that a device is probably sitting on the card screens, not just that it is active. The switch "show where I am on the cards" in the options room is on by default and stops all sending (it does not hide other people from you); the setting is kept on this device only. Receivers treat every field as untrusted: the sender is already verified by the live channel, the community and room must be ones this device is in, the sender must be a known member of that community, the data is a small object of a few short fields, and a card shows at most 6 dots and then "+N". A hostile member can only claim to be on cards in communities they are really in, and only as themselves (events are signed); they can flood only within the channel's rate limits. Older apps ignore the events (they note "newer version" once).
* **Owner looks** (a room's or the community card's ASCII pattern on its card, the pattern behind the chat, and the backdrop strength) are one more optional map (`looks`) in the same owner-signed style document, so they reveal exactly what the colours reveal: nothing new to the relay (a table commit: its size and time). Members can read them; only the owner's signature makes them count. Every value is bounded and checked when the owner signs and when a device receives the document (pattern numbers 0 to 31, strength 0 to 200 percent, at most 500 entries, valid ids; one bad part makes the whole document unbelievable), and an app that does not know a pattern number shows its automatic choice. A document without looks is byte for byte what it was, and 0.3.0 and older read a document that has them (the unknown field is skipped). Each change is one more table commit in the relay's log, so the app sends a look only when the owner releases or commits, never while a slider moves. Limit: an owner running 0.3.0 or older who changes colours, locks or clears a wall writes a document without the looks, so the looks revert to automatic until a newer app of the owner sets them again.
* **Walls on cards.** A channel card shows that room's wall (the same `wall.*` events, lock and clear). A **community card has a wall of its own**: its strokes and snapshots travel as `cwall.d` / `cwall.s` (and the questions `cwall.q` / `cwall.h`) in one text room of the community (the lowest-id one this device can send in; every device accepts them from any room of the community it is in, so changing the carrier loses nothing), under a separate key in the same capped, encrypted wall state. They are ordinary live events, so the relay learns what it learns for any packet (size and time, nothing of kind or content), and the members of the carrier room, who are members of the community, can read them; people who are not in that room get the drawing in a snapshot. Rooms never mix the two: a `cwall.*` event can not draw on a room's wall, and older apps (which only know `wall.*`) never draw it anywhere; they note "newer version" once, as for any live event they do not know. Its lock and clear are the existing `locked` and `wall` fields of the signed style document, keyed by the community id (older apps filter those to room ids and ignore it). Opening, resting on or scrolling past a card sends nothing; only drawing does (at most 2 events a second per person, nothing while idle), plus the one request for the wall when someone starts drawing and nobody is known to be around.
* **Live events** (a best-effort channel for small short-lived data, carrying the camera-stack order and the shared wall) no longer travel as MLS application messages, and no longer enter the relay's log. See "The live channel" below. A relay from before the channel, or a client that finds none, falls back to the old way (ordinary padded MLS messages through the log, four a second per room); the guarantees of that path are unchanged.
* **The camera stack order and the shared wall** ride on live events, so the relay learns nothing beyond "a packet of this size was posted now by this device". Everything inside (which tile a person holds, the order, the drawing, the questions and answers) is end-to-end encrypted like a message. What members learn: who is dragging which tile (visible to people in the call), and who drew which cells (a cell carries its author's account, which is how ties are broken). On the live channel an event is not in the relay's log, so the apps may send about ten a second per room (coalesced per kind), nothing while idle, and nothing into a room where nobody is around to see it. Through the log fallback each event is a permanent log entry, so the old limits (four a second per room) apply there. The wall is kept on each device inside the encrypted state (a capped field, written on a 20 second debounce). **Lock and clear** are fields of the owner-signed style document in the community table (a set of locked rooms and a per-room wall generation), so they are durable, reach late joiners and cannot be forged: a lock makes receivers drop strokes from anyone but the owner, a clear raises the generation so strokes and snapshots of the old generation are ignored by everyone, including a device that was offline. A snapshot (a member's copy of the wall, sent to someone who just opened the room) carries per-cell authorship that only the sender vouches for, since cells are not individually signed; so while a wall is locked only the owner's snapshot counts, every author a snapshot names must be a member of the room, and one sender may introduce only a few new authors. Older apps note "newer version" for these events and ignore them; they also read a style document that has the new fields (unknown fields are skipped, and a document without them is byte-for-byte what it was).
* No sealed-sender style anonymity; no protection of IP addresses.
* **The browser edition** (Linux, Windows, macOS: `bridge` plus a window in Brave, Chrome, Chromium or Edge) is the development bridge (`dev_bridge`) built with its `devbridge` feature, and it speaks the whole RPC over loopback HTTP on a fixed port (7420). Loopback is shared by every user and program on the computer, so it is protected in layers: (1) the launcher gives each start of the bridge a random 256-bit secret and opens the window at `http://127.0.0.1:<port>/#t=<one-time ticket>` (the secret itself is never in an address or on the browser's command line, which other users can read); the fragment is never sent to a server, so it is in no request line or log; the page trades the ticket for the secret once (`POST /session`, valid two minutes) and keeps it for that window only, takes it out of the address bar and sends it as `X-Megatron-Secret` with every `/rpc` and `/update-*` call, which the bridge compares in constant time; the secret is kept in a file only the user can read (mode 600) in the install or data folder; (2) the window uses a browser profile of its own, so extensions of the everyday profile do not see the page; (3) before opening, the launcher asks whatever is on the port to prove it knows the secret (`/hello`, a hash of the secret and a fresh nonce) and refuses to open onto anything else, so another user who got the port first is not handed the window; (4) Host and Origin are checked as before, so a web page cannot reach it, and on Linux a connection from another user's socket is refused. What this does **not** stop: a program running as the same user (it can read the secret file or the browser's memory), and an extension or script inside the window itself. **Open mode:** a bridge started without a secret (a launcher from before this, your own script or service, the test rigs) still works exactly as before, protected by Host/Origin and, on Linux, the same-user check only; the page shows a plain notice when that is an installed copy. A bridge from before this change is replaced, on the next start, by a protected one when the launcher is current; an update refreshes an older Linux launcher script in the install folder (the old one is kept as `megatron.old`) and, on Windows and macOS, the launcher program itself (on macOS the new launcher travels inside `ui/` and the next bridge swaps it into `Contents/MacOS` and signs the app again, see docs/UPDATES.md).

**Opening as a tab** (Settings, per device; `open-as` file or `MEGATRON_OPEN=tab`) trades the second layer for convenience: the page then lives in the person's everyday browser profile, so that profile's extensions and anything else that can read its pages can see mega's messages and the secret in `sessionStorage`; the window mode, the default, exists to prevent that. The address of a tab never holds the secret: it holds a one-time ticket (120 seconds, spent by the first `POST /session`, file mode 600), because the browser's history, sync and extensions would keep any address. A program of the same user can still read the ticket file, as it can the secret file; another user's program cannot (file mode, and the same-user socket check on Linux). Not covered by any of this: the Tauri desktop app and the iPhone app, which have no bridge (the page reaches the core through the shell's own channel). The call hand-off (`callbridge`) is separate and unchanged: its own one-time secret, one room.
* The Tauri page keeps `withGlobalTauri` on: turning it off would change nothing, because `window.__TAURI_INTERNALS__` is there either way. The defence against script in the page is that page input is validated and escaped, and the CSP.
* Timestamps are the sender's claim, capped at five minutes ahead of the reader's clock. Order comes from the log.
* After the relay loses its data, clients say so and re-register, but groups have to be re-created by new invites: their logs are gone.

## Out of scope in stage 1

Push notifications, iOS, federation, bots, large communities (hundreds of members), moderation tooling beyond kick/ban, history transfer between devices.
